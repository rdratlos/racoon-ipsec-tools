# Kate syntax highlighting for racoon.conf

`racoon.xml` is a [Kate](https://kate-editor.org/) syntax-highlighting
definition for Racoon's configuration file format. It is generated
directly from the authoritative grammar in
[`src/racoon/cftoken.l`](../../src/racoon/cftoken.l), so its keyword
lists stay in sync with what Racoon actually accepts.

It was bootstrapped from KDE's stock `Cisco.xml` highlighting definition,
since Cisco IOS config syntax (block-structured, `#`-commented,
whitespace-indented) is a reasonable starting point for `racoon.conf`.

## Installing

Kate (and other applications built on KSyntaxHighlighting, such as
KWrite and KDevelop) load user syntax definitions from:

```
~/.local/share/org.kde.syntax-highlighting/syntax/
```

Copy the file there and restart Kate:

```
mkdir -p ~/.local/share/org.kde.syntax-highlighting/syntax/
cp misc/kate/racoon.xml ~/.local/share/org.kde.syntax-highlighting/syntax/
```

System-wide installation (requires root) goes into the equivalent
`/usr/share/org.kde.syntax-highlighting/syntax/` directory instead.

Kate picks the highlighting automatically for files named `racoon.conf`,
`racoon-*.conf`, or `*.racoon.conf`. For any other filename, select
"Racoon IPSec Tools" from Kate's mode menu (bottom status bar, or
*Tools -> Highlighting -> Configuration*).

## Regenerating

The file is generated by [`scripts/gen-kate-syntax.pl`](../../scripts/gen-kate-syntax.pl):

```
scripts/gen-kate-syntax.pl src/racoon/cftoken.l > misc/kate/racoon.xml
```

`make kate-syntax` (from the repository root, after `./configure`) does
the same thing. Regenerate and commit the result whenever
`cftoken.l` gains, renames, or removes a keyword.

## How the categories are derived

The script buckets every bare-word lexer pattern in `cftoken.l` by the
token its action returns:

| Kate list    | Grammar meaning                                          |
|--------------|-----------------------------------------------------------|
| `sections`   | Keywords that open a top-level `{ ... }` block (`remote`, `sainfo`, `listen`, `proposal`, ...) |
| `keywords`   | Option/directive names inside a block (`lifetime`, `exchange_mode`, `pfs_group`, ...) |
| `datatypes`  | Algorithm and identifier-type names (`aes`, `sha256`, `fqdn`, ...) |
| `constants`  | Enumerated values for an option (`on`/`off`, `yes`/`no`, `x509`, `main`, `strict`, ...) |
| `units`      | Time and size units (`sec`, `hour`, `KB`, `byte`, ...) |
| `protocols`  | Upper-layer protocol names (`esp`, `ah`, `tcp`, ...) |

Because `cftoken.l` reuses the same word for different tokens in
different lexer states (e.g. `byte` is both a lifetime unit and a
`LIFETYPE_BYTE` option keyword), a handful of words legitimately appear
in more than one list. This is a simplification made for readable
highlighting, not a re-implementation of Racoon's lexer states.

Numbers, `0x` hex values, `"quoted strings"`, IPv4/IPv6-ish address
literals, `{ }` block braces (with code folding), and `#` comments are
handled directly in the generated `<contexts>` section, independent of
the keyword lists above.
