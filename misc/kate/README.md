# Kate syntax highlighting for racoon.conf

`racoon.xml` is a [Kate](https://kate-editor.org/) syntax-highlighting
definition for Racoon's configuration file format. It is generated
directly from the authoritative grammar in
[`src/racoon/cftoken.l`](../../src/racoon/cftoken.l), so its keyword
lists stay in sync with what Racoon actually accepts.

It was bootstrapped from KDE's stock `Cisco.xml` highlighting definition,
since Cisco IOS config syntax (block-structured, `#`-commented,
whitespace-indented) is a reasonable starting point for `racoon.conf`.

## Installing

Kate (and other applications built on KSyntaxHighlighting, such as
KWrite and KDevelop) load user syntax definitions from:

```
~/.local/share/org.kde.syntax-highlighting/syntax/
```

Copy the file there and restart Kate:

```
mkdir -p ~/.local/share/org.kde.syntax-highlighting/syntax/
cp misc/kate/racoon.xml ~/.local/share/org.kde.syntax-highlighting/syntax/
```

System-wide installation (requires root) goes into the equivalent
`/usr/share/org.kde.syntax-highlighting/syntax/` directory instead.

Kate picks the highlighting automatically for files named `racoon.conf`,
`racoon-*.conf`, or `*.racoon.conf`. For any other filename, select
"Racoon IPSec Tools" from Kate's mode menu (bottom status bar, or
*Tools -> Highlighting -> Configuration*).

## Block indentation

`racoon.xml` also declares `indenter="cstyle"`. This tells Kate to use
its built-in C-style indentation script for this syntax by default —
no per-file-type configuration needed. Since `racoon.conf` blocks are
`{ }`-delimited and `;`-terminated just like C, pressing Enter inside a
`remote { ... }` or `proposal { ... }` block indents one level deeper,
and typing the closing `}` dedents back to match its opening line. `#`
comments indent with the surrounding block rather than being pinned to
column 0 (the C indenter only does that for its own `C`/`C++` modes,
not for ours).

If you'd rather use a different indenter, override it per-document via
*Tools -> Indentation*, or repository-wide with a
[modeline](https://docs.kde.org/stable_kf6/en/kate/katepart/config-variables.html)
comment at the top of a file, e.g. `# kate: indent-mode normal;`.

## Compatibility

`racoon.xml` declares `kateversion="5.0"`. This is a floor, not a target:
none of the XML constructs this file uses (`keyword`, `DetectChar`,
`RegExpr`, `Int`, `AnyChar`, `IncludeRules`, `defStyleNum`, or the
`indenter` attribute) have ever had a documented minimum version above
that. Kate silently skips loading a syntax file whose declared
`kateversion` exceeds its own — e.g. Ubuntu 18.04 "Bionic" ships
KTextEditor 5.44, so a file declaring anything above that never loads,
with no error beyond a debug-log line. Keep this attribute at the
lowest value that's actually true; don't bump it "to be current" when
touching this file, only when a change genuinely starts using a newer
feature.

The `<IncludeRules context="##Alerts"/>` in the `Comment` context (for
`TODO`/`FIXME`/`XXX` markers inside `#` comments) is deliberately
`##Alerts`, not the newer `##Comments` convenience wrapper that some
stock KDE syntax files use — `Comments.xml` bundling `##Alerts` +
`##Modelines` + `##SPDX-Comments` postdates Bionic-era Kate, and a
reference to a highlighting definition that doesn't exist yet fails
the same silent way `kateversion` does: `IncludeRules` targets need
the same "oldest thing that's actually true" discipline, not just the
`kateversion` attribute.

Don't copy constructs from a modern stock `.xml` file into this one on
the assumption they're safe — verify locally instead (see below).

## Validating changes

Kate gives no useful error for either failure mode above short of a
debug-log line an end user won't see. Checking that the file is
well-formed XML (e.g. `xmllint --noout misc/kate/racoon.xml`) is not
enough — it says nothing about whether Kate can actually load it. For
that you need the real KSyntaxHighlighting engine: install
`libkf5syntaxhighlighting-tools` (Debian/Ubuntu) or the equivalent
`kate-syntax-highlighter` CLI for your distro, then:

```
mkdir -p ~/.local/share/org.kde.syntax-highlighting/syntax/
cp misc/kate/racoon.xml ~/.local/share/org.kde.syntax-highlighting/syntax/
kate-syntax-highlighter -l | grep -i racoon        # confirm it's recognized at all
kate-syntax-highlighter -s "Racoon IPSec Tools" \
    -f ansi src/racoon/samples/roadwarrior/client/racoon.conf   # any warning prints to stderr
```

A clean run prints colorized output with nothing on stderr. This
won't catch a version-specific gap like the `##Comments` one above
(the CLI tool is whatever version your distro currently ships), but it
does catch outright typos, unknown `context`/`attribute` references,
and similar mistakes before they ever reach a user.

## Regenerating

The file is generated by [`scripts/gen-kate-syntax.pl`](../../scripts/gen-kate-syntax.pl):

```
scripts/gen-kate-syntax.pl src/racoon/cftoken.l > misc/kate/racoon.xml
```

`make kate-syntax` (from the repository root, after `./configure`) does
the same thing. Regenerate and commit the result whenever
`cftoken.l` gains, renames, or removes a keyword.

## How the categories are derived

The script buckets every bare-word lexer pattern in `cftoken.l` by the
token its action returns:

| Kate list    | Grammar meaning                                          |
|--------------|-----------------------------------------------------------|
| `sections`   | Keywords that open a top-level `{ ... }` block (`remote`, `sainfo`, `listen`, `proposal`, ...) |
| `keywords`   | Option/directive names inside a block (`lifetime`, `exchange_mode`, `pfs_group`, ...) |
| `datatypes`  | Algorithm and identifier-type names (`aes`, `sha256`, `fqdn`, ...) |
| `constants`  | Enumerated values for an option (`on`/`off`, `yes`/`no`, `x509`, `main`, `strict`, ...) |
| `units`      | Time and size units (`sec`, `hour`, `KB`, `byte`, ...) |
| `protocols`  | Upper-layer protocol names (`esp`, `ah`, `tcp`, ...) |

Because `cftoken.l` reuses the same word for different tokens in
different lexer states (e.g. `byte` is both a lifetime unit and a
`LIFETYPE_BYTE` option keyword), a handful of words legitimately appear
in more than one list. This is a simplification made for readable
highlighting, not a re-implementation of Racoon's lexer states.

Numbers, `0x` hex values, `"quoted strings"`, IPv4/IPv6-ish address
literals, `{ }` block braces (with code folding), and `#` comments are
handled directly in the generated `<contexts>` section, independent of
the keyword lists above.
