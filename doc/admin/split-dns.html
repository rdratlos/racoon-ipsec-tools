Split-DNS & Routing Scripts

How phase1-up.sh/phase1-down.sh (also called hooks) configure per-domain DNS resolution and split-tunnel routing when a road-warrior client connects, what they will and will not touch on your system, and how to diagnose them with racoon-dns-detect.

1. Overview & design constraints

When a road-warrior client completes Phase 1 and Mode Config negotiation, the gateway may hand back an internal address, a list of split-include networks, one or more internal DNS servers, and a list of split-DNS domains. phase1-up.sh turns that into: a dedicated interface carrying the assigned address, routes for the split-include networks, and DNS configuration scoped to the given domains only — so lookups for corp.example.com go over the tunnel while everything else keeps using your normal resolver. phase1-down.sh reverses exactly what was applied when the tunnel goes down.

The scripts follow a fixed set of rules, regardless of which backend ends up handling DNS on your system:

  • Never a persistent system change. Nothing here edits /etc/nsswitch.conf, enables a service, or otherwise reconfigures your machine beyond the lifetime of the VPN session. Where a genuine reconfiguration would help (e.g. resolving a PARALLEL_UNLINKED resolv.conf landscape), the scripts report a recommendation — they never apply it themselves.
  • Owns only the SPD entries it installs. racoon does not install SPD policy for a Mode Config initiator (policy generation is responder-only) — without one, split-include traffic the scripts just routed onto the tunnel has nothing telling the kernel to encrypt it, which previously produced a kernel-ACQUIRE reconnect loop. The scripts install exactly the entries their own routes need, record their full selector text, and tear them down the same way as every other step — never spdflush, never setkey -F, never anything they didn't themselves install.
  • Every value from the gateway is untrusted input. Mode Config attributes are validated against a strict whitelist before use; a value that fails validation is dropped, never partially used.
  • DNS goes up last, comes down first. On connect, DNS is only configured once the tunnel and routes are in place; on disconnect, DNS is reverted before routes and the interface are torn down.
  • The VPN address lives on a dedicated dummy interface (racoon0 by default), never on your physical network card — this avoids ARP-leaking the internal address onto your LAN. Split-include routes still point out your physical interface; only the packets' source address is anchored via the dummy interface's address. If NetworkManager is running on the system at all — even when a different backend is handling DNS, e.g. it manages your physical interfaces while systemd-resolved is reached directly — it will very likely auto-manage this freshly-created interface the moment it appears; the scripts detect that and tear it down through NetworkManager's own device-removal path first (falling back to a plain interface delete if that turns out not to be needed), rather than deleting it out from under NetworkManager's bookkeeping.
  • No hardcoded fallback network. If the gateway sends no split-include networks and no internal DNS servers, there is nothing to route through the tunnel — phase1-up.sh reports that and refuses, rather than guessing a network that might not even be reachable through this gateway.

2. Installation

These scripts are a real installed component of the build (src/racoon/scripts/Makefile.am), not example material — a plain ./configure && make install installs all four into $(sysconfdir)/racoon/scripts (/etc/racoon/scripts with the packaging defaults), alongside hooks.conf:

/etc/racoon/scripts/racoon-hook-lib.sh   # shared library (sourced by everything below)
/etc/racoon/scripts/phase1-up.sh         # racoon phase1-up script
/etc/racoon/scripts/phase1-down.sh       # racoon phase1-down script
/etc/racoon/scripts/racoon-dns-detect    # standalone diagnostic CLI

Point racoon at phase1-up.sh/phase1-down.sh in your client-side racoon.conf:

remote anyremote
{
    ...
    script "/etc/racoon/scripts/phase1-up.sh" phase1_up;
    script "/etc/racoon/scripts/phase1-down.sh" phase1_down;
}

Building from a source checkout without installing (development, or running the test suite) works the same way against the in-tree copy at src/racoon/scripts/ — nothing about the scripts themselves differs between the two locations.

All four scripts are plain POSIX sh — no bashisms, no arrays, no [[ ]] — and run under dash, bash, and NetBSD's /bin/sh unmodified. They must stay together in the same directory: phase1-up.sh/phase1-down.sh/racoon-dns-detect all source racoon-hook-lib.sh from the directory they themselves live in — this is also why racoon-dns-detect is installed alongside the others rather than into sbindir with the rest of racoon's own binaries; run it via its installed path (or symlink it onto your own PATH if you prefer).

3. Configuration (hooks.conf)

phase1-up.sh and phase1-down.sh read an optional configuration file, hooks.conf, at /etc/racoon/hooks.conf (or wherever RACOON_HOOK_CONF points). See etc/racoon/hooks.conf.sample for the fully-commented version; the keys are:

KeyDefaultMeaning
backendautoForce a specific DNS backend, or let phase1-up.sh detect one (see §4).
on_dns_failurewarnwarn always exits 0; report exits 1 when a required step fails but leaves changes already applied in place; rollback does the same and additionally undoes every change that run applied first. None of the three reject the tunnel — racoon does not consult phase1-up.sh's exit code for that. (abort is accepted as a deprecated alias for report.)
debug_level00–3, see §6. RACOON_HOOK_DEBUG in the environment overrides this without editing the file.
dummy_ifaceracoon0Name of the dedicated interface carrying the VPN address and DNS profile.
allow_resolv_conf_overwritenoWhether the none (fallback) backend may overwrite /etc/resolv.conf directly when no supported resolver manager is detected. Refused by default (a reported failure, subject to on_dns_failure) rather than silently redirecting every lookup on the system to the VPN resolver — see §4.

4. Supported DNS backends

Backend detection asks, in order: NetworkManager's own D-Bus RcManager property (never guessed from file layout — NetworkManager's own "symlink" mode can legitimately write a plain file), then nsswitch.conf's hosts: line for an nss-resolve entry, then the glibc resolver's actual symlink target, then a content-signature scan of /etc/resolv.conf, then whether resolvconf/dnsmasq are present and active. Set backend explicitly in hooks.conf to skip detection.

BackendSplit-DNS?Mechanism
resolved yes Per-link DNS servers and routing-only domains (~domain) via resolvectl (or systemd-resolve on older systems — the two have incompatible flag grammar and are never conflated). default-route is only ever available via resolvectl — systemd-resolve has no equivalent at all — and even then only once feature-probed (resolvectl --help), never assumed from a version number. See the capability table just below.
networkmanager yes, if a routing-capable DNS plugin is active A dedicated dummy connection profile (racoon-vpn-dns) fully configured in one nmcli connection add call before first activation. Routing-only domains require systemd-resolved, dnsmasq, or dnsconfd to also be listed in NetworkManager's own dns= setting; with a plain dns=default configuration NetworkManager has no concept of per-domain routing, and phase1-up.sh says so loudly rather than silently doing a full redirect.
resolvconf no Classic resolvconf(8) merges nameservers with no per-domain routing concept — the VPN resolver becomes authoritative for every lookup while the tunnel is up. Reported as such, not represented as real split-DNS.
dnsmasq yes One server=/domain/ip line per domain/server pair in /etc/dnsmasq.d/racoon-vpn — never a bare server=ip line, which would replace dnsmasq's global upstream. Refuses outright (a reported failure, not a silent redirect) if the gateway sent no split-DNS domains at all.
none (fallback) no No supported resolver manager detected. Refused by default (allow_resolv_conf_overwrite = no, reported as a failed required step) — set it to yes to opt in to writing /etc/resolv.conf directly (backed up first), a full DNS redirect for the duration of the tunnel, explicitly reported as not real split-DNS.

Within the resolved backend specifically, resolvectl and systemd-resolve are not interchangeable — one capability genuinely differs between them (everything else either tool supports equally, per the tool-capability probe in racoon-hook-lib.sh):

Capabilityresolvectlsystemd-resolve
Per-link DNS serversyesyes
Routing-only domains (~domain)yesyes
Revert a link's DNS configyesyes
Flush resolver cachesyesyes
default-route (scope without domains)if feature-probed presentnever

The practical consequence: on a systemd-resolve-only system (older Bionic-era hosts in particular) with a gateway that pushes DNS servers but no split-DNS domains, there is no scoping mechanism available at all — phase1-up.sh reports this explicitly and skips DNS configuration entirely (§9) rather than silently making the VPN resolver authoritative for every lookup on the link.

A negative NetworkManager DNS priority is never used. NetworkManager treats a negative ipv4.dns-priority as "exclusive," dropping every other active connection's DNS servers from the merged /etc/resolv.conf — this silently took out a physical uplink's own DNS server in earlier iterations of these scripts. The dummy profile always uses a small positive priority (50).

5. Diagnosing with racoon-dns-detect

racoon-dns-detect answers "what would phase1-up.sh do on this system right now?" without a VPN session, without root, and without changing anything:

# Survey resolv.conf and the DNS capability matrix, explain each conclusion
racoon-dns-detect --detect --explain

# Preview the exact step plan for sample (or real) DNS parameters --
# nothing below --dry-run is ever executed
racoon-dns-detect --dry-run --explain \
    --dns=10.0.12.53 --domains=corp.example.com --routes=10.0.12.0/24

# Machine-readable output for scripting
racoon-dns-detect --detect --format=kv

Two resolv.conf landscape problems it will flag by name:

  • DIVERGENT — the file glibc actually reads (per nsswitch.conf/the resolver symlink) disagrees with at least one other backend-generated copy on the system.
  • PARALLEL_UNLINKED — reported precisely when /etc/resolv.conf is a plain file, not a symlink, and at least two other surveyed locations are backend-generated copies (/etc/resolv.conf itself is excluded from that count — an ordinary NetworkManager dns=dnsmasq setup, one generated copy plus /etc/resolv.conf, is not this condition). racoon-dns-detect prints a recommendation (symlink /etc/resolv.conf to the authoritative backend's output, or set that backend's own file-ownership setting) — it never applies this itself (design rule in §1).

6. State, logs, and teardown

Every applied step is journaled to /run/racoon/hook-state.<remote-addr>.<generation> as it succeeds — this file, not a re-run of detection, is phase1-down.sh's only source of what to undo. Undoing happens in the reverse of apply order, which is what makes both "DNS down first" and, since brief 3 §E, "SPD before routes/address/dummy" (§1) fall out automatically rather than needing to be separately-maintained rules.

Only DNS-group steps roll back within a single phase1-up.sh run if a later required DNS step fails — SPD entries, routes, and the dummy interface do not get the same in-transaction treatment, by design: DNS specifically was the historical cause of a real reconnect-loop bug (an unscoped VPN resolver left registered), while a partially-applied route or SPD entry from a run that failed part way through is not itself harmful in the same way. Those already-succeeded steps stay applied, recorded in the state file with their own undo commands, to be cleaned up by the next phase1-down.sh run exactly like any other teardown — the state file is the sole guard either way. The residual case this doesn't cover is a hard crash between "a step applied" and "a matching phase1-down.sh ever runs" (e.g. SIGKILL, or SIGTERM under a shutdown path that doesn't reliably invoke the scripts — a known daemon-side gap, tracked separately and out of scope for the scripts themselves); until whatever runs next for that peer, the state file is what's left of the record.

State is matched per remote address, not per remote address+port: the port racoon reports floats across a NAT-T rebind, so it is not part of a session's identity. Each phase1-up.sh run allocates a new, monotonically-numbered generation for its peer address without touching any earlier generation still on disk; each phase1-down.sh run consumes the generation matching its own IKE_COOKIE — racoon's ISAKMP cookie pair for the negotiation, unique per Phase 1 attempt and stable from setup through teardown — rather than assuming file order. That distinction matters whenever more than one generation is live for the same peer at once: a teardown for an old session and the setup of its replacement landing within the same second (which live testing showed does happen), or a generation from an earlier session that was never cleanly torn down and is still sitting on disk (an orphan — a later, unrelated teardown for the same peer must not consume it just because it happens to be the oldest). phase1-down.sh never guesses at cleaning up a generation that isn't its own, even one that looks orphaned: a live generation with no matching IKE_COOKIE may just as well be a genuinely concurrent session for the same peer, or an earlier run's partial-failure retry still waiting for its own teardown to claim it — there is no safe way to tell "orphan" apart from "not mine yet" without reintroducing exactly the file-order guessing this design replaced. An accumulated orphan is a sign something upstream didn't clean up after itself (see the previous paragraph) and is left for an administrator to investigate, not silently swept up. Teardown is best-effort: one failed undo does not block the rest from running, and a generation with anything left to undo is marked consumed rather than deleted, so a later retry picks it up again rather than the failure going unrecorded. Consumed generations are reaped automatically (oldest first) once more than 5 accumulate for a peer, or after 24 hours — a live, unconsumed generation (including an orphan with no matching IKE_COOKIE left to claim it) is never touched by reaping.

Verbosity is controlled by debug_level in hooks.conf (or RACOON_HOOK_DEBUG in the environment, which always wins):

LevelDestination
0 quietsyslog only: errors, warnings, the final one-line summary.
1 normal+ the full per-step report on stderr.
2 verbose+ exact command line and exit code per step, mirrored to /run/racoon/hook.trace.
3 trace+ captured stdout/stderr per step, plus the evidence behind each detection decision.

7. Security model

  • Every Mode Config value the gateway sends (internal address, DNS servers, split-include networks, split-DNS domains) is whitelist-validated before use — IPv4/CIDR/domain-name/port syntax and count limits. The whole value is rejected on the first invalid element; nothing is trimmed or "fixed" and partially used.
  • 0.0.0.0, loopback, and multicast addresses are rejected as DNS servers.
  • Plan steps are built entirely from already-validated tokens before any external command runs, so the single execution point that evaluates them never sees an un-validated value from the network.
  • setkey is only ever invoked in -c (stdin) mode with a single, fully-constructed spdadd/spddelete line built entirely from already-validated selector components — never a batch file, never -F. LOCAL_ADDR/REMOTE_ADDR/LOCAL_PORT/REMOTE_PORT (racoon's own Phase 1 environment) are whitelist-validated before they can reach that line, since a newline or shell metacharacter smuggled through would inject arbitrary setkey commands.

8. Troubleshooting

"Split-DNS domains cannot be isolated" warning

Seen with backend = networkmanager when NetworkManager's own dns= setting has no per-domain routing plugin (plain dns=default). Add systemd-resolved or dnsmasq to dns= in NetworkManager.conf, e.g. dns=default,systemd-resolved, or set backend = resolved in hooks.conf if systemd-resolved is already running.

A required step keeps failing and the tunnel exits nonzero

Set debug_level = 2 (or RACOON_HOOK_DEBUG=2) and re-run; the trace at /run/racoon/hook.trace has the exact failing command and its output. racoon-dns-detect --dry-run --explain with the same DNS parameters will show the same plan without needing an active tunnel.

A previous disconnect never fully cleaned up

Check /run/racoon/hook-state.* — a non-empty file (not .consumed, not .cookie) means something failed to undo last time. Since phase1-down.sh matches by exact IKE_COOKIE, not just REMOTE_ADDR, a hand-run retry needs that generation's own cookie: read it from the matching hook-state.<remote-addr>.<generation>.cookie sidecar and export it as IKE_COOKIE alongside REMOTE_ADDR before invoking phase1-down.sh, or just inspect the state file's undo commands directly and run them by hand; each line is id  type  outcome  undo_command, tab-separated.

9. Known limitations

  • IPv4 only — no IPv6 split-DNS/routing support yet.
  • resolvectl's default-route subcommand is feature-probed (via resolvectl --help) rather than version-gated, because the systemd release that introduced it could not be confirmed against upstream release notes.
  • On a systemd-resolve-only resolved system (no default-route support at all — §4) with a gateway that pushes DNS servers but no split-DNS domains, there is no scoping mechanism available. phase1-up.sh reports this and skips DNS configuration entirely rather than registering an unscoped VPN resolver for every lookup on the link — internal names behind the tunnel will not resolve until the gateway is configured to send split-DNS domains, or the client is on a host with resolvectl instead.
  • resolvconf and the /etc/resolv.conf fallback backend both apply a full DNS redirect for the tunnel's duration, not per-domain routing — this is a property of those backends, not a bug in the scripts.
  • The road-warrior topology assumes one active gateway connection per racoon instance; the connection id used for state-file naming is derived from REMOTE_ADDR alone (not REMOTE_PORT, which floats across a NAT-T rebind).
